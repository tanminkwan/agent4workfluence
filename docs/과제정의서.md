# 과제 정의서 — 명세 기반 Tool 생성·사용 Agent 3종 (첫 대상: Workfluence)

- 작성일: 2026-10-12
- 상태: 초안 (미정 항목 확정 대기)
- 저장소: https://github.com/tanminkwan/agent4workfluence.git

## 1. 목적

Workfluence(금융 폐쇄망용 위키·문서 협업 시스템)의 공개 REST API(`/api/v1`) 명세를 따라가며, 그 API를 쓰는 AI agent가 Workfluence의 채팅 창에서 사람 요청을 수행하게 한다. 이를 위해 역할이 다른 agent 3종을 만든다.

| # | agent | 성격 | 한 줄 역할 |
|---|---|---|---|
| 1 | Detection agent | rule/code 기반 (AI 아님) | API 명세(YAML)를 확인·버전 관리하고, 변경분을 식별한다. |
| 2 | Manufacture agent | 명세 기반 생성 | 명세에 맞춰 inference agent용 tool을 만들고, 변경분이 생기면 upgrade 한다. 또 tool을 RAG 시스템(AI Pro Plus)에 색인해 자연어로 필요한 tool을 검색할 수 있게 한다. |
| 3 | Inference agent | AI agent | 대기하다가 text 요청을 받으면 tool을 사용해 수행한다. 요청 입구는 자체 REST API가 기본이고, 현재 Workfluence 채팅 참여가 더해진다. |

흐름: Detection(변경 식별) → Manufacture(tool 생성·갱신) → Inference(tool 사용).

### 1.0 agent별 LLM

| agent | LLM | 이유·영향 |
|---|---|---|
| Detection | 없음 (rule/code) | AI를 쓰지 않는다. |
| Manufacture | **아주 똑똑한 모델 (Opus급)** | 명세를 읽고 tool을 설계·설명·묶음하는 일은 어렵고 품질이 중요하다. 만들 때 한 번 쓰는 비용이므로 최상위 모델을 쓴다. |
| Inference | **gpt-oss급 모델** | 요청마다 돌아 비용·속도·사내 운영이 중요하다. 상대적으로 작은 모델이다. |

**Inference가 작은 모델이라는 점이 설계에 주는 영향**
- tool을 모델이 다루기 쉽게 만드는 것이 Manufacture의 핵심 책임이다. 이름과 설명이 명확하고, 입력 칸이 적고 단순하고, 한 tool이 한 가지 일을 하게 한다. 필요한 경우 여러 API 호출을 묶은 상위 tool로 만든다.
- tool 전체를 컨텍스트에 싣지 않고 AI Pro Plus RAG로 필요한 tool만 찾아 준다. 작은 모델의 선택 부담을 줄이는 장치이기도 하다.
- 오류 응답은 모델이 스스로 고칠 수 있도록 원인과 다음 행동이 드러나게 돌려준다.
- 호출 규약(기준 버전, 재시도, 호출 한도 등)은 모델에 맡기지 않고 tool 코드가 처리한다.
- 모델은 설정으로 바꿀 수 있어야 한다(agent별 모델·엔드포인트 설정). 특정 제공사에 묶지 않고, gpt-oss처럼 OpenAI 호환 API를 쓰는 모델도 같은 방식으로 연결한다.

### 1.1 범용성 지향

이 3종은 Workfluence 전용 서비스가 아니라, **"API 명세를 확인하고, 그에 맞는 tool을 만들고, 그 tool을 사용한다"는 범용 기능**이다. Workfluence는 첫 번째 대상(첫 적용 사례)일 뿐이다. 설계와 구현은 가급적 범용성을 지향한다.

- **타겟은 여럿일 수 있다.** 타겟 하나는 식별자(`targetId`)와 아래 설정 묶음으로 정의한다. 타겟을 등록하고, 고르고, 바꿔 쓸 수 있어야 한다(multi-target).
  1. **타겟 시스템의 API key(token)** — 환경변수·설정으로 받는다.
  2. **타겟 spec 경로(URL)** — 명세 위치(와 변경 확인용 해시 URL)를 설정으로 받는다.
  3. (선택) 타겟 정책·어댑터 설정.
- **범용 기반(코어)**: 타겟이 무엇이든 같은 방식으로 도는 부분이다. 타겟 설정만으로 명세 수집·버전 보관·diff(Detection), 명세→tool 생성·upgrade(Manufacture), tool을 쓰는 요청 수행(Inference)이 돌아야 한다. **Inference agent가 요청을 받는 자체 REST API**도 타겟과 무관한 코어이며, 요청마다(또는 세션마다) 어느 타겟을 쓸지 고른다.
- **타겟 식별**: 한 타겟에서 나온 모든 산출물을 `targetId`로 묶어 식별한다.
  - 명세 사본·버전 이력·diff, 그 명세로 Manufacture가 만든 tool(과 tool 버전), 타겟 token, 타겟 정책 설정, 타겟 종속 어댑터가 모두 한 타겟에 속한다.
  - 다른 타겟의 명세·tool·token이 섞이지 않는다. 같은 이름의 동작이 두 타겟에 있어도 충돌하지 않는다(tool 이름공간을 타겟별로 분리).
- **tool은 종속물이 아니다**: Manufacture가 만든 tool은 명세에서 만든 산출물이지 특정 타겟에 박힌 코드가 아니다. 다만 어느 타겟의 것인지는 `targetId`로 표시한다. Workfluence API로 만든 tool도 마찬가지다.
- **타겟 종속 어댑터(선택)**: 특정 타겟에만 있는 기능은 코어에 넣지 않고 그 타겟의 어댑터로 분리한다. Inference agent가 사용한다.
  - 예: Workfluence 채팅 API(`/api/v1/chat/ws`)로 요청을 받는 채널, 장문 결과를 올릴 Workfluence 게시판·메일.
  - 어댑터가 없어도 코어는 동작한다.
- **타겟 선택과 전환**: 타겟 목록을 보고, 사용할 타겟을 고르고, 바꿀 수 있어야 한다. Detection은 타겟마다 따로 명세를 확인하고, Manufacture는 타겟마다 따로 tool 집합을 관리하고, Inference는 선택된 타겟의 tool 집합과 어댑터를 쓴다.
- 타겟별 정책(tool 제외 기준 등)은 코어의 하드코딩이 아니라 타겟 설정으로 둔다. 예: Workfluence의 admin 태그 제외, 위험 동작 기본 끔.
- 새 타겟을 붙일 때 코어를 고치지 않고 타겟 설정(필요하면 어댑터)만 더하는 것을 목표로 한다. 첫 타겟은 Workfluence다.

## 2. 범위

### 2.1 Detection agent

**하는 일**
- 타겟(첫 대상은 Workfluence)의 API 명세(YAML)를 받아 `targetId`별로 저장하고, 스스로 버전을 관리한다. 명세의 `info.version`은 `1.0.0`으로 고정이고 changelog·deprecated 표시도 없어서, 변경 기준은 sha256 하나다.
- 해시가 바뀌면 `openapi.yaml`을 받아 이전 사본과 줄 단위로 diff 하고, 동작 단위로도 비교해서 변경분(동작 추가·삭제, 경로·입력·응답·scope 변경 등)을 식별한다.
- 변경이 있으면 변경분을 Manufacture agent에게 넘긴다.

**명세 확인 방식**
- 명세 받기: `GET {BASE}/api/v1/openapi.yaml` (인증 불필요, 키 정렬 YAML, OpenAPI 3.1). `/api/v1/openapi.json`도 있다. (`workf` 확인)
- 변경 여부 선확인: `GET {BASE}/api/v1/openapi.sha256`. 해시가 같으면 전체를 받지 않는다.
- 확인 시점 세 가지:
  1. Detection agent를 재시작할 때
  2. 하루 한 번
  3. Workfluence가 webhook으로 호출할 때 — **나중에** 한다(사용자 결정). 지금 Workfluence에는 명세 변경 webhook이 없고 계획도 없다(`workf` 확인). 우선 1·2번만 구현하고, webhook 입구는 Workfluence가 지원하면 추가한다.

**원칙**
- AI를 쓰지 않는다. 같은 입력이면 같은 결과를 내는 코드로 만든다.
- 명세 파일은 키 정렬 YAML이라 같은 코드면 늘 같은 글이 나온다. 해시가 다르면 명세가 바뀐 것이다.
- 호환 정책: v1은 더하기만 한다(필드·경로 추가). 빼거나 뜻을 바꾸면 v2다. 모르는 응답 필드는 무시한다. 따라서 삭제·변경이 보이면 v2 전환 신호로 보고 사람에게 알린다.
- 받은 명세를 버전별로 보관해서, 임의 두 버전 사이의 변경을 다시 볼 수 있어야 한다.

### 2.2 Manufacture agent

**하는 일**
- 명세(YAML)를 읽고 inference agent가 쓰기 좋은 tool을 만든다.
- Detection agent가 알려준 변경분에 대해 기존 tool을 upgrade 한다. 동작이 추가되면 tool을 더하고, 바뀌면 고치고, 삭제되면 정리한다.

**tool 검색 RAG (외부 시스템 AI Pro Plus 사용)**
- Qdrant 기반 RAG 관리 시스템 **AI Pro Plus**가 이미 있고 REST API를 제공한다. **RAG 시스템은 이 프로젝트가 개발하지 않는다.** Manufacture agent는 그 REST API의 클라이언트로서 tool을 색인하고 갱신한다.
- 만든 tool을 AI Pro Plus에 등록해, 자연어로 필요한 tool을 검색할 수 있게 한다. (예: "페이지에 댓글 달기" → 댓글 쓰기 tool)
- 색인 단위는 tool 하나다. tool 이름, 설명, 입력·출력, 소속 `targetId`, tool 버전, scope를 함께 저장한다.
- 타겟별로 분리한다. 검색은 선택된 타겟의 tool만 대상으로 한다(`targetId`로 구분 — 방식은 AI Pro Plus의 구조에 맞춘다).
- 명세 변경분으로 tool을 upgrade 할 때 색인도 함께 갱신한다. 추가는 등록, 변경은 재등록, 삭제는 제거한다. 색인과 tool 버전이 어긋나지 않게 한다.
- 검색 결과에는 tool 식별자와 근거(일치한 설명)를 담아 Inference agent가 바로 쓸 수 있게 한다.
- tool 전체를 Inference agent의 컨텍스트에 싣지 않고, 필요한 tool만 찾아 쓰게 하는 것이 목적이다.
- AI Pro Plus는 범용 RAG 시스템이므로 타겟과 같은 방식으로 "설정으로 연결하는 외부 시스템"으로 다룬다(URL·token은 설정).

**AI Pro Plus 연동 방식 (`aipro-plus` 세션 확인, 서버 코드 기준이며 실제 호출 검증 전)**
- 명세: `GET {base}/openapi.json` (FastAPI 자동 생성, Swagger `{base}/docs`). 로컬 dev는 `http://localhost:28000`, nginx 경유는 `https://llm-agent.mwm.local`. 시험·운영 base URL은 배포 환경별이라 사용자 확인이 필요하다.
- 인증: 서버가 `NON_LOGIN_SERVICE=true`이면 헤더·키 없이 모두 nobody(Admin 권한)로 처리된다. false(IDP 모드)이면 nobody는 불가하고 Bearer API key가 필요하다. 선택 헤더 `X-Virtual-User: aiagent-manufacture`로 로그·통계 집계 주체를 지정할 수 있다(비로그인 모드에서만).
- production 인증: `Authorization: Bearer <API_KEY>`(표준 Bearer, 커스텀 헤더 없음). AI Pro Plus가 키를 보관하지 않고 IDP에 위임 검증한다(타임아웃 3초). 유효하면 `api-key-user`(Admin)로 처리되어 키별 권한 구분(읽기 전용 등)은 없다. 키는 IDP 관리자가 IDP 대시보드의 "관리자 REST API Key"에서 발급하며(AI Pro Plus에 발급 API 없음), 유효기간·폐기 정책은 IDP 운영 측에 확인해야 한다. 키가 무효이면 401 `{"detail":"Not authenticated"}`이고 키 오류와 IDP 장애는 구분되지 않는다. IDP 모드에서는 `X-Virtual-User`가 무시되어 호출자별 구분이 안 된다. 그 외 API 규약은 test와 production이 같으므로, 클라이언트는 base URL과 `Authorization` 헤더 유무만 환경 설정으로 분기한다.
- 구성: 컬렉션 생성 `POST /api/collections`(`collection_name`은 영문·숫자·`_`·`-`), 지식 등록 시 `domain_id`가 필수라서 먼저 도메인을 만든다(`POST /api/domains`). 컬렉션이 이미 있으면 500이 날 수 있어 생성 전에 목록 조회한다.
- tool 등록·수정: `POST /api/rag/knowledge` (`collection_name`, `domain_id`, `content`, `extended_content`, `source`, `point_id`). `point_id`를 지정하면 같은 ID를 덮어써서 수정이 된다. point ID는 UUID 또는 unsigned int만 가능하므로 `uuid5(namespace, "targetId:toolName")` 같은 결정적 UUID로 멱등 upsert 한다.
- 삭제: `DELETE /api/rag/knowledge/{collection_name}/{point_id}`. 일괄 삭제 `DELETE /api/rag/bulk-delete`(`domain_id` 또는 `source` 필수). 타겟 통째 삭제는 `DELETE /api/collections/{name}?delete_vector=true`.
- 저장 필드: `content`(이것만 임베딩되어 검색 대상), `extended_content`, `domain_id`, `source`, `created_at`. **자유 메타데이터 필드는 없다**(`targetId`·버전·scope 전용 필드 없음). 그래서 `content`는 tool 이름+설명 요약(수백 자)으로 짧게 만들고, tool 전체 명세·버전·scope는 `extended_content`(JSON 문자열)에 담는다. `source`에는 `targetId/toolName@버전` 규약 문자열을 쓴다.
- 검색: `POST /api/rag/search` (`collection_id`(null·"all"은 전체), `domain_id`, `query`, `search_method`(`vector`|`text_matching`), `limit`). 서버 필터는 컬렉션과 `domain_id`뿐이다. `score` 임계값 파라미터가 없어 클라이언트에서 컷한다. 응답은 score 내림차순이고 `extended_content`가 같이 와서 검색 결과로 tool 명세를 바로 쓸 수 있다.
- 임베딩·청킹은 AI Pro Plus 서버가 맡는다(클라이언트 지정 불가). 청킹 없이 content 1건이 1벡터이므로 tool 1개 = 1건으로 넣는다.
- 제한: rate limit 코드 없음, nginx 기본 body 1MB 제한 가능성, 배치 API 없음(tool N개 = POST N회 순차), 단건 upsert마다 임베딩 호출이 동기로 돌아 느릴 수 있다. 오류는 `{"detail": "..."}`(400·404·422, 그 외 500).
- 이 프로젝트의 설계 영향: 타겟 구분은 **타겟별 컬렉션 `tools_<targetId>`** 를 제안한다(타겟 삭제·초기화가 쉽고 서버 필터가 컬렉션 단위로 가능). 타겟이 매우 많아지면 단일 컬렉션 + 타겟별 `domain_id`로 바꾼다. 타겟 간 통합 검색은 `collection_id`를 생략하면 된다.

**tool 대상 범위 (Workfluence 설정 기준 — 코어가 아니라 대상별 설정으로 둔다)**
- (Workfluence 기준) 공개 API는 66개 동작이다. 이 중 51개를 대상으로 하고, 관리(admin) 15개는 제외한다.

| 묶음 | tool | scope | 기본값 |
|---|---|---|---|
| 탐색·읽기 | 스페이스 목록·조회, 페이지 트리, 페이지 읽기, 검색, 라벨 목록, 라벨별 페이지, 분류 목록, 템플릿 목록, 첨부 목록·받기 | read | 켬 |
| 이력 | 버전 목록, 옛 버전 읽기, 버전 diff | read | 켬 |
| 소통 | 댓글 목록·쓰기·고치기·지우기, 알림 목록·미읽음 수·읽음 처리(개별·전체) | read/write | 켬 |
| 작성 | 페이지 생성·수정, 라벨 붙이기·떼기 | write | 켬 |
| 위험 동작 | 페이지 삭제·이동·버전 복원, 첨부 올리기·삭제, 휴지통 복원(페이지) | write | **끔** (설정으로 켬) |

**원칙**
- 변경분 처리는 되돌릴 수 있어야 한다. tool도 버전을 두고, upgrade 전 버전으로 돌아갈 수 있어야 한다.
- 새로 생긴 동작이 admin 태그이거나 위험 동작이면 자동으로 켜지 않고 사람의 확인을 거친다.
- 생성한 tool은 시험 스택에서 실호출로 검증한 뒤 색인에 반영하고 inference agent가 쓰게 한다.

### 2.3 Inference agent

**요청 입구 (채널)**
- **기본: 자체 REST API.** Inference agent는 text 형태의 요청을 받는 REST API를 기본으로 가진다. 요청 text를 받아 tool로 수행하고 결과를 응답한다. 채팅과 무관하게 동작한다.
- **현재 추가 채널: Workfluence 채팅 (타겟 종속 어댑터).** 지금은 Workfluence가 제공하는 채팅에만 참여하지만, 채팅은 REST 입구와 같은 수행 로직을 쓰는 하나의 채널(어댑터)이다. 채널이 늘어도 수행 로직은 바뀌지 않는다.
- 채널과 수행 로직을 분리한다. 채널은 "요청 text 받기 → 수행 → 결과 돌려주기"만 맡는다.

**하는 일**
- 평소에는 대기한다.
- (채팅 채널) Workfluence 채팅 창에 초대되면, 하나의 user로 접속해 사람과 대화한다.
- 대화 중 나오는 요청(예: 페이지 찾기·요약, 댓글·문서 작성)을 수행한다. 요청에 필요한 tool은 AI Pro Plus RAG에서 자연어로 검색해 찾고, 그 tool로 수행한다.

**채팅 채널의 응답 규칙** (사용자 확정 — 채팅 창에만 적용한다)
- 목적은 명령 수행이다. 채팅 창에는 구구절절 쓰지 않고, 수행 여부와 결과 위치만 짧게 알린다.
- "채팅 창 요약해줘"처럼 결과물이 긴 요청은 결과를 **메일 또는 Workfluence 게시판(페이지)에 올리고**, 채팅 창에는 절대 길게 쓰지 않는다. 채팅 창에는 올린 위치(링크)만 알린다.
- REST 채널은 요청에 대한 응답으로 결과를 돌려준다. 장문도 응답 본문에 담을 수 있는지, 비동기로 처리할지는 설계 때 정한다.
- "길다"의 기준(글자 수 등)은 설계 때 정한다.

**채팅 API (Workfluence 설계 중, `workf` 확인)**
- 채팅 UI와 API는 Workfluence 본체가 만든다(이 프로젝트의 범위 밖). 설계서는 Workfluence 저장소 `docs/P21_설계서_Chat.md`(브랜치 `impl-phase21`)에 있고, 구현은 아직 시작 단계다.
- 방 단위 채팅(1:1 `direct`, 여럿 `group`)이다. headless 클라이언트(우리 agent)는 공개 API 토큰으로 접속한다.
  - REST: `/api/v1/chat/*` (방 목록·만들기·초대·나가기, 메시지 읽기·보내기, 읽음 표시, 사용자 찾기). 읽기는 `read`, 쓰기는 `write` scope.
  - WebSocket: `/api/v1/chat/ws`. `Authorization: Bearer <토큰>` 헤더로 연결하고, 토큰을 URL 질의 문자열로 보내는 것은 받지 않는다.
  - 프레임: `hello`, `send`, `ack`, `message`, `room`(방이 생기거나 초대·나감), `error`. 30초 주기 ping/pong.
  - 놓친 메시지는 REST로 `afterSeq` 조회해 메운다. 보낼 때 `clientMsgId`를 붙이면 재전송이 한 번만 반영된다.
  - 메시지는 평문이다(마크다운·HTML 아님). 길이 상한 기본 4000자.
- **초대 알림**: 별도 webhook은 없다. agent가 WebSocket에 항상 연결해 두고 `room` 프레임으로 초대를 알게 된다. 그래서 inference agent의 "대기"는 이 연결을 유지하는 것이다.
- 아직 확정되지 않았으므로(구현 시작 단계, 값은 착수 때의 가정) 이 프로젝트의 채팅 연동은 Workfluence 구현을 확인하며 맞춘다. 공개 명세(`openapi.yaml`)에 REST가 더해지면 Detection·Manufacture agent가 같은 방식으로 반영한다. WebSocket은 OpenAPI로 표현되지 않아서, 명세 머리말과 API사용가이드를 본다.
- 채팅 API가 공개되기 전까지는 Detection agent와 Manufacture agent를 먼저 만든다.

### 2.4 범위 밖 (명시적 제외)

| 제외 대상 | 이유 |
|---|---|
| 채팅 UI와 채팅 API | Workfluence 본체가 가져야 할 기능이다. |
| admin 태그 15개: `/audit`, `/settings/policy`, `/users/**` | 일반 사용자 활동이 아니다. 계정·정책·감사는 사람이 한다. |
| 스페이스 생성·삭제·멤버·상태 변경 | 구조·권한 변경은 사람이 한다. |
| 분류·템플릿 생성·수정·삭제 | 같은 이유. 목록 조회만 한다. |
| 페이지 내보내기, 스페이스 휴지통 복원 | inference agent 활동에 필요하지 않다. |
| 토큰 발급·폐기, 비밀번호 초기화 | API에 없다. 화면에서 사람이 한다. |

## 3. 설계 원칙

1. **명세가 정본**: 서버의 `/api/v1/openapi.yaml`이 유일한 기준이다. Detection agent가 받은 사본은 버전별로 보관하되 손으로 고치지 않는다.
2. **최소 권한**: 토큰 scope를 확인해, 토큰에 없는 권한의 tool은 등록하지 않는다. admin tool은 만들지 않는다.
3. **안전한 쓰기**: 페이지 수정은 기준 버전이 필수다(불일치 시 409). 409는 다시 읽어 재시도한다.
4. **호출 한도 준수**: 토큰당 읽기 120회/분, 쓰기 30회/분. 429는 `Retry-After`만큼 기다린 뒤 재시도한다.
5. **재시도 규칙**: 5xx는 읽기만 재시도한다. 쓰기는 응답을 알 수 없으면 읽어서 확인한 뒤 다시 보낸다. 400·401·403·404는 재시도하지 않는다.
6. **오류 처리**: `error.code`로 분기하고 `requestId`를 agent에 그대로 전달한다.
7. **본문 형식**: 마크다운만 쓴다. 서버가 원시 HTML·그림·허용 밖 링크를 400으로 거절한다.
8. **비밀 관리**: 토큰은 `.env`(권한 600, `.gitignore` 대상)로만 다룬다. 코드·문서·로그·메모리에 남기지 않는다.
9. **agent 독립성**: 3종은 서로 느슨하게 연결한다. Detection의 변경분과 Manufacture의 tool을 파일·버전 같은 명시적 산출물로 주고받아, 각각 따로 시험하고 재시작할 수 있게 한다.
10. **범용성**: 코어는 타겟 설정(token, spec URL)과 Inference agent 요청 API를 기반으로 하고, Workfluence 고유 값(URL·태그·채팅 API 등)을 하드코딩하지 않는다. 여러 타겟을 `targetId`로 구분해 등록·선택·전환하고, 산출물은 타겟별로 분리한다. 타겟 종속 부분은 설정·선택 어댑터로 둔다. 첫 대상은 Workfluence다.

### 3.1 개발 원칙 (사용자 지시)

1. **SOLID 원칙 준수.** 특히 코어와 타겟 어댑터, 채널(REST·채팅) 어댑터는 인터페이스로 분리하고 구체 구현에 의존하지 않는다(DIP). 새 타겟·채널은 기존 코드를 고치지 않고 더한다(OCP).
2. **하드코딩하지 않는다.** URL, token, 모델명, 경로, 임계값, 한도, 제외 규칙은 설정으로 둔다. 비밀은 코드·문서·로그에 남기지 않는다(원칙 8).
3. **TDD (red → green)**: 실패하는 테스트를 먼저 쓰고(red), 통과시키는 최소 구현을 한 뒤(green), 정리한다. 구현 전에 테스트가 먼저 있어야 한다.
4. **phase 분할**: 작업을 phase로 나누고, phase마다 과제를 끝까지 수행·완료한 뒤 다음 phase로 넘어간다. 완료 기준은 phase의 요구사항 충족과 test 결과서다.
5. **산출물은 `docs/`에 phase별로 쓴다.** phase마다 요구사항(과제) 정의 → 설계 → test 결과서 순서로 남긴다.

**문서 구조**

```
docs/
  과제정의서.md            # 전체 과제 (phase 0)
  phase1_<이름>/
    1_요구사항정의.md
    2_설계.md
    3_test결과서.md
  phase2_<이름>/ ...
```

- test 결과서에는 실행한 명령, 통과·실패 건수, 확인하지 못한 것(실호출 검증 여부 포함)을 사실대로 적는다.
- 한 phase의 문서가 끝나기 전에 다음 phase 구현을 시작하지 않는다.

## 5. 확정된 결정

- admin tool은 모두 제외한다. (사용자 확정, 2026-10-12)
- 문서는 `docs/`에 둔다.
- Inference agent는 text 요청을 받는 자체 REST API를 기본으로 가진다. Workfluence 채팅은 그 위에 더해지는 채널이다. (사용자 확정, 2026-10-12)
- 타겟은 여럿일 수 있고, 타겟을 `targetId`로 식별해 등록·선택·전환한다. 명세·tool·token·정책·어댑터는 타겟별로 분리한다. Manufacture가 만든 tool은 타겟 종속물이 아니라 산출물이며 `targetId`로 소속만 표시한다. (사용자 확정, 2026-10-12)
- Workfluence 채팅은 Inference agent가 쓰는 타겟 종속 어댑터다. (사용자 확정, 2026-10-12)
- 3종은 Workfluence 전용이 아니라 범용 기능이다. Workfluence는 첫 대상이며, 가급적 범용성을 지향한다. (사용자 확정, 2026-10-12)
- 채팅 UI는 이 프로젝트의 범위가 아니다. Workfluence가 가져야 할 기능이다. (사용자 확정, 2026-10-12)
- agent는 Detection(rule/code) · Manufacture · Inference(AI) 3종이다. (사용자 확정, 2026-10-12)
- Detection agent의 명세 확인 시점은 재시작, 하루 1회다. webhook 호출은 나중에 추가한다. (사용자 확정, 2026-10-12)
- AI Pro Plus 인증: 시험(test) 환경까지는 api-key 없이 nobody 모드로 쓴다. production에서는 api key를 받아 쓴다. api key는 타겟 token처럼 설정으로 받는다. (사용자 확정, 2026-10-12)
- Manufacture agent는 tool을 RAG 시스템 AI Pro Plus(Qdrant 기반, REST API 제공)에 색인해 자연어로 검색하게 한다. AI Pro Plus는 이미 있는 외부 시스템이며 이 프로젝트가 개발하지 않는다. 색인은 타겟별로 분리하고 tool upgrade와 함께 갱신한다. (사용자 확정, 2026-10-12)
- LLM: Manufacture agent는 Opus급, Inference agent는 gpt-oss급 모델을 쓴다. Detection은 LLM을 쓰지 않는다. (사용자 확정, 2026-10-12)
- Manufacture agent는 기계적 부분은 코드 생성, tool 설명·묶음은 LLM 보조로 만든다. (사용자 확정, 2026-10-12)
- 변경분 반영 시 사람 확인은 삭제, 권한 변경, admin·위험 동작 추가에만 거친다. (사용자 확정, 2026-10-12)
- 명세 버전 보관소는 저장소 내 파일 + Git 이력이다. (사용자 확정, 2026-10-12)
- Inference agent는 채팅 창에 짧게만 답한다. 장문 결과는 메일 또는 Workfluence 게시판에 올리고 채팅 창에는 쓰지 않는다. (사용자 확정, 2026-10-12)
