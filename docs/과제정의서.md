# 과제 정의서 — 명세 기반 Tool 생성·사용 Agent 3종

- 작성일: 2026-10-12
- 상태: 초안 (미정 항목 확정 대기)
- 저장소: https://github.com/tanminkwan/agent4workfluence.git
- 이 문서는 phase 0 산출물이다. 시스템 구조는 [`시스템아키텍처.md`](시스템아키텍처.md)에 있다.

## 1. 목적

타겟 시스템의 API 명세를 확인하고(Detection), 그 명세로 AI가 쓰기 좋은 tool을 만들고(Manufacture), 그 tool로 사람의 text 요청을 수행하는(Inference) agent 3종을 만든다.

**과제 범위의 타겟은 하나, Workfluence다.** Workfluence는 금융 폐쇄망용 위키·문서 협업 시스템이며 공개 REST API(`/api/v1`)를 제공한다. 이번 과제에서 타겟을 더 붙이지는 않지만, 나중에 타겟이 추가되는 것을 전제로 범용성을 고려해 설계한다(1.3절).

### 1.1 agent 3종

| # | agent | 성격 | 역할 |
|---|---|---|---|
| 1 | Detection | rule/code 기반 (AI 아님) | 타겟의 API 명세를 받아 버전 관리하고, 변경분을 식별한다. |
| 2 | Manufacture | LLM 보조 생성 | 명세로 Inference agent용 tool을 만들고, 변경분이 생기면 upgrade 한다. tool을 RAG 시스템(AI Pro Plus)에 색인해 자연어로 검색할 수 있게 한다. |
| 3 | Inference | AI agent | 자체 REST API로 text 요청을 받아, 필요한 tool을 검색해 수행한다. Workfluence 채팅에도 참여한다(어댑터). |

흐름: Detection(변경 식별) → Manufacture(tool 생성·갱신·색인) → Inference(tool 검색·사용).

### 1.2 agent별 LLM

| agent | LLM | 이유 |
|---|---|---|
| Detection | 없음 | 같은 입력이면 같은 결과를 내는 코드로 만든다. |
| Manufacture | 아주 똑똑한 모델 (Opus급) | tool 설계·설명·묶음은 어렵고 품질이 중요하다. 만들 때만 쓰므로 비용 부담이 작다. |
| Inference | gpt-oss급 모델 | 요청마다 돌아서 비용·속도·사내 운영이 중요하다. 상대적으로 작은 모델이다. |

LLM 접속 방식(엔드포인트·인증)은 그 agent의 phase에서 설계한다.

**Inference가 작은 모델이라는 점이 설계에 주는 영향**
- tool을 작은 모델이 다루기 쉽게 만드는 것이 Manufacture의 핵심 책임이다. 이름과 설명이 명확하고, 입력 칸이 적고, 한 tool이 한 가지 일을 한다. 필요하면 여러 API 호출을 묶은 상위 tool로 만든다.
- tool 전체를 컨텍스트에 싣지 않고 RAG로 필요한 tool만 찾아 준다. 작은 모델의 선택 부담을 줄이는 장치이기도 하다.
- 오류 응답은 모델이 스스로 고칠 수 있도록 원인과 다음 행동을 보여 준다.
- 호출 규약(기준 버전, 재시도, 호출 한도 등)은 모델에 맡기지 않고 tool 실행 코드가 처리한다.
- 모델은 설정으로 바꿀 수 있어야 한다. 특정 제공사에 묶지 않고, OpenAI 호환 API 모델도 같은 방식으로 연결한다.

### 1.3 범용성 (타겟 추가 대비)

이 3종은 Workfluence 전용 서비스가 아니라 "명세를 확인하고, tool을 만들고, 그 tool을 쓴다"는 범용 기능이다. 이번 과제의 타겟은 Workfluence 하나지만, 나중에 타겟을 붙일 때 코어를 고치지 않아도 되게 만든다.

- **코어와 타겟을 분리한다.** 코어는 타겟이 무엇이든 같은 방식으로 돈다. 타겟마다 다른 것은 타겟 설정과 타겟 어댑터로 둔다.
- **타겟 설정은 타겟별 `.env`로 둔다.** 타겟 token, spec URL, 호출 한도 같은 값을 타겟별 환경변수로 받는다. 파일 이름과 변수 이름 규칙은 Phase 1 설계에서 정한다.
- **타겟 식별**: 타겟마다 `targetId`를 둔다. 명세 사본·버전 이력·diff, tool과 tool 버전, RAG 색인, 어댑터를 모두 `targetId`로 묶는다. tool 이름공간도 타겟별로 나눈다.
- **tool은 타겟 종속물이 아니다.** Manufacture가 명세에서 만든 산출물이며, 소속만 `targetId`로 표시한다.
- **타겟 종속 어댑터**: 특정 타겟에만 있는 기능은 그 타겟의 어댑터로 분리한다. 예를 들어 Workfluence 채팅 채널, 장문 결과를 올릴 Workfluence 게시판이 있다. 어댑터가 없어도 코어는 동작한다.
- **구현 범위**: 이번 과제에서는 Workfluence에 필요한 경우만 구현한다. 다른 타겟을 위한 경우는 interface만 만들고 구현은 비워 둔다. 예를 들어 해시 URL이 없는 타겟, 정렬되지 않은 명세, JSON 명세, 여러 타겟 사이의 선택·전환이 그렇다.

## 2. 범위

### 2.1 Detection agent

**하는 일**
- 타겟의 API 명세를 받아 `targetId`별로 저장하고, 버전을 관리한다.
- 명세가 바뀌면 이전 버전과 diff 하고, 동작 단위로도 비교해서 변경분(동작 추가·삭제, 경로·입력·응답·scope 변경)을 식별한다.
- 변경분을 `spec-store`(Detection 전용)에 쓰고 변경분 ID를 응답한다. Manufacture를 직접 부르지 않는다. Manufacture는 Detection의 변경분 조회 API로 내용을 읽는다(시스템아키텍처 1절).
- 받은 명세는 버전별로 보관해서, 임의의 두 버전 사이 변경을 다시 볼 수 있게 한다. 손으로 고치지 않는다.

**확인 시점**
- Detection은 변경 식별 API가 호출될 때만 실행한다. 일정을 스스로 갖지 않는다.
- "재시작 시", "하루 한 번" 같은 실행 일정은 외부 scheduler나 workflow 도구가 맡고, 그쪽의 환경변수로 설정한다.
- 타겟이 webhook으로 알리는 방식은 나중에 한다. 지금 Workfluence에는 webhook이 없다.

**구현 범위 (Workfluence 조건만 구현)**

| 경우 | Workfluence | 이번 과제 |
|---|---|---|
| 변경 확인 | 해시 URL(`openapi.sha256`)을 먼저 보고, 같으면 명세를 받지 않는다 | 구현 |
| 명세 형식 | OpenAPI 3.1 YAML, 키 정렬 (같은 코드면 늘 같은 글) | 구현 |
| diff | 줄 단위 + 동작 단위 | 구현 |
| 해시 URL이 없는 타겟 | — | interface만 둔다 (명세를 받아 직접 해시 계산) |
| 키 정렬이 보장되지 않는 명세 | — | interface만 둔다 (정규화 후 diff) |
| JSON 명세 | Workfluence도 `openapi.json`을 주지만 YAML을 쓴다 | interface만 둔다 |
| webhook 수신 | 없음 | 하지 않는다 (나중에) |

### 2.2 Manufacture agent

**하는 일**
- 명세를 읽고 Inference agent가 쓰기 좋은 tool을 만든다. 기계적인 부분은 코드 생성으로, tool 설명과 묶음은 LLM 보조로 만든다.
- Detection이 넘긴 변경분으로 tool을 upgrade 한다. 동작이 추가되면 tool을 더하고, 바뀌면 고치고, 삭제되면 정리한다.
- tool을 AI Pro Plus(Qdrant 기반 RAG 관리 시스템, 외부 시스템)에 색인해 자연어로 검색할 수 있게 한다. 예를 들어 "페이지에 댓글 달기"로 검색하면 댓글 쓰기 tool이 나와야 한다. AI Pro Plus는 이 프로젝트가 개발하지 않고 REST API 클라이언트로만 쓴다. 연동 방식은 Phase 2에서 설계하며, 지금까지 확인한 내용은 부록 A에 있다.

**원칙**
- tool은 Manufacture 서비스의 MCP server(`manufacture-mcp`, Streamable HTTP)가 서빙하고 실행한다. Inference는 MCP client로 tool을 받아 쓴다. tool 정의 형식은 미정 항목 4에서 정한다.
- 색인 단위는 tool 하나다. tool upgrade와 색인 갱신이 어긋나지 않게 한다(추가는 등록, 변경은 재등록, 삭제는 제거).
- 변경은 되돌릴 수 있어야 한다. tool에도 버전을 두고 이전 버전으로 돌아갈 수 있게 한다.
- 사람 확인은 삭제, 권한 변경, admin·위험 동작 추가에만 거친다. 확인 절차는 미정 항목 12에서 정한다.
- 생성한 tool은 시험 환경에서 실호출로 검증한 뒤 색인에 반영한다.
- 어떤 동작을 tool로 만들지는 타겟 설정이 정한다. Workfluence의 대상 범위는 4.3절에 있다.

### 2.3 Inference agent

**요청 입구 (채널)**
- **기본은 자체 REST API다.** text 요청을 받아 수행하고 결과를 응답한다. 타겟과 무관한 코어다.
- **Workfluence 채팅은 타겟 종속 어댑터다.** REST와 같은 수행 로직을 쓰는 하나의 채널이다. 채널은 "요청 text 받기 → 수행 → 결과 돌려주기"만 맡고, 수행 로직과 분리한다.

**하는 일**
- 요청에 필요한 tool을 AI Pro Plus에서 자연어로 검색해 찾고, 그 tool로 수행한다.
- (채팅 채널) Workfluence 채팅 방에 초대되면 하나의 user로 대화에 참여해 요청을 수행한다. 채팅 API는 Workfluence가 설계 중이며, 확인한 내용은 부록 B에 있다.

**채팅 채널의 응답 규칙** (채팅 창에만 적용)
- 목적은 명령 수행이다. 채팅 창에는 수행 여부와 결과 위치만 짧게 알린다.
- "채팅 창 요약해줘"처럼 결과가 긴 요청은 메일이나 Workfluence 게시판(페이지)에 올린다. 채팅 창에는 절대 길게 쓰지 않고 올린 위치만 알린다.
- REST 채널은 결과를 응답 본문으로 돌려준다. 장문을 어떻게 처리할지(본문에 담기, 비동기)는 Phase 3 설계에서 정한다.

### 2.4 범위 밖

| 제외 대상 | 이유 |
|---|---|
| Workfluence 이외의 타겟 | 이번 과제의 타겟은 하나다. 추가를 위한 interface만 둔다. |
| 채팅 UI와 채팅 API | Workfluence 본체가 가져야 할 기능이다. |
| AI Pro Plus(RAG 시스템) 개발 | 이미 있는 외부 시스템이다. 클라이언트로만 쓴다. |
| Workfluence admin 동작 15개 (`/audit`, `/settings/policy`, `/users/**`) | 일반 사용자 활동이 아니다. 계정·정책·감사는 사람이 한다. |
| Workfluence 스페이스 생성·삭제·멤버·상태 변경, 분류·템플릿 생성·수정·삭제 | 구조·권한 변경은 사람이 한다. 목록 조회만 한다. |
| Workfluence 페이지 내보내기, 스페이스 휴지통 복원 | Inference agent 활동에 필요하지 않다. |
| 토큰 발급·폐기, 비밀번호 초기화 | API에 없다. 화면에서 사람이 한다. |
| 명세 변경 webhook 수신 | 나중에 한다. |

## 3. 설계 원칙 (코어)

1. **명세가 정본이다.** 타겟 서버가 내는 명세가 유일한 기준이다. 받은 사본은 손으로 고치지 않는다.
2. **최소 권한.** 타겟 token의 권한을 확인해, 없는 권한이 필요한 tool은 등록하지 않는다. 제외 규칙은 타겟 설정이 정한다.
3. **호출 규약은 코드가 지킨다.** 재시도, 호출 한도, 충돌 처리, 오류 해석은 타겟 어댑터가 처리하고 모델에 맡기지 않는다. 규약의 값은 타겟 설정에 둔다.
4. **비밀 관리.** token과 api key는 `.env`(권한 600, Git 제외)로만 다룬다. 코드·문서·로그·커밋에 남기지 않는다.
5. **agent 독립성.** 서비스마다 독립된 Docker container로 돈다(Manufacture는 `manufacture`와 `manufacture-mcp` 2개). 저장소는 소유 서비스만 접근하고, 다른 서비스는 소유 서비스의 조회 API나 MCP로만 읽는다. 실행을 서로 연쇄로 부르지 않고, 순서는 바깥(사람의 curl, 나중에 workflow 도구)이 정한다.
6. **범용성.** 코어에 타겟 고유 값(URL, 경로, 태그, 규칙)을 넣지 않는다(1.3절).

### 3.1 개발 원칙

1. **SOLID 원칙 준수.** 코어와 타겟 어댑터, 채널 어댑터는 interface로 분리하고 구체 구현에 의존하지 않는다(DIP). 새 타겟·채널은 기존 코드를 고치지 않고 더한다(OCP).
2. **하드코딩하지 않는다.** URL, token, 모델명, 경로, 임계값, 한도, 제외 규칙은 설정으로 둔다.
3. **TDD (red → green).** 실패하는 테스트를 먼저 쓰고(red), 통과시키는 최소 구현을 한 뒤(green), 정리한다.
4. **phase 분할.** phase마다 과제를 끝까지 완료한 뒤 다음 phase로 넘어간다. 완료 기준은 그 phase의 요구사항 충족과 test 결과서다.
5. **산출물은 `docs/`에 phase별로 쓴다.** 요구사항 정의 → 설계 → test 결과서 순서로 남긴다.

```
docs/
  과제정의서.md            # 전체 과제 (phase 0)
  phase1_<이름>/
    1_요구사항정의.md
    2_설계.md
    3_test결과서.md
  phase2_<이름>/ ...
```

test 결과서에는 실행한 명령, 통과·실패 건수, 확인하지 못한 것(실호출 검증 여부 포함)을 사실대로 적는다.

## 4. Workfluence 타겟 설정

코어가 아니라 Workfluence 타겟의 설정·어댑터로 들어가는 내용이다. 값은 타겟별 `.env`로 받는다.

### 4.1 접속과 명세

| 항목 | 내용 |
|---|---|
| 시험 스택 | `https://wf.internal:8444` (자체 서명 인증서, 사내 프록시 시 `--noproxy '*'`) |
| 인증 | `Authorization: Bearer <토큰>`. 토큰은 사람이 화면에서 발급한다. scope는 `read`·`write`·`admin`. |
| 명세 | `GET {BASE}/api/v1/openapi.yaml` (인증 불필요, OpenAPI 3.1, 키 정렬), 변경 확인 `GET {BASE}/api/v1/openapi.sha256` |
| 버전 표시 | `info.version`은 `1.0.0` 고정이고 changelog·deprecated 표시가 없다. 변경 기준은 sha256 하나다. |
| 호환 정책 | v1은 필드·경로를 더하기만 한다. 빼거나 뜻을 바꾸면 v2다. 모르는 응답 필드는 무시한다. 삭제·변경이 보이면 v2 전환 신호로 보고 사람에게 알린다. |
| 감사 | 토큰으로 한 일도 감사로그에 남는다(`jti` 포함). |
| 명세 사본 | `/data/tiffanie/projects/workfluence/docs/spinoff/public-api/` |
| 문의 | 다른 Claude 세션 `workf` |

### 4.2 호출 규약

| 항목 | 내용 |
|---|---|
| 호출 한도 | 토큰당 읽기 120회/분, 쓰기 30회/분. 초과 시 429와 `Retry-After`(초). 계정 하나가 읽기·쓰기 한도를 함께 쓴다. |
| 재시도 | 429는 기다렸다 재시도한다. 5xx는 읽기만 재시도한다. 쓰기는 결과를 모르면 읽어서 확인한 뒤 다시 보낸다. 400·401·403·404는 재시도하지 않는다. |
| 충돌 | 페이지 저장 시 기준 버전이 필수이고, 불일치하면 409다. 다시 읽고 재시도한다. |
| 오류 | `{"error":{"code","message","requestId"}}`. `code`로 분기하고 `requestId`를 그대로 전달한다. |
| 본문 | 마크다운만 쓴다. 원시 HTML·그림·허용 밖 링크는 400으로 거절된다. |

## 5. 확정된 결정

- agent는 서비스마다 독립된 Docker container로 동작하고 실행을 서로 연쇄로 부르지 않는다. Detection은 변경 식별 API 1개, Manufacture는 변경 반영 실행 API 1개를 열고, 지금은 사람이 curl로 실행한다. 나중에 n8n·Windmill·Prefect 같은 workflow 도구에 끼울 수 있게 만든다. (사용자 확정, 2026-10-12)
- Manufacture는 container 2개로 나눈다: `manufacture`(변경 반영 실행)와 `manufacture-mcp`(MCP server, Streamable HTTP로 tool 서빙·실행). Inference는 MCP client로 tool을 쓴다. 타겟 token은 Manufacture만 가진다. (사용자 확정, 2026-10-12)
- 빌드·테스트·실행 등 모든 작업은 container 안에서 한다. 실행 구성은 `docker-compose.yml` 하나이고, image build는 compose와 독립한다(compose에 `build:`를 두지 않고 이미지를 참조만 한다). (사용자 확정, 2026-10-12)
- `spec-store`는 Detection만 접근한다. Manufacture는 Detection이 제공하는 조회 API로 변경분을 읽는다. (사용자 확정, 2026-10-12)
- 과제 범위의 타겟은 Workfluence 하나다. 타겟 추가를 전제로 범용성을 고려해 설계한다. (사용자 확정, 2026-10-12)
- 타겟 설정은 타겟별 환경변수(`.env`)로 둔다. (사용자 확정, 2026-10-12)
- Workfluence 조건에 해당하는 경우만 구현한다. 다른 경우는 interface만 만들고 구현은 비워 둔다. (사용자 확정, 2026-10-12)
- AI Pro Plus와 LLM 연동은 해당 phase에서 설계한다. (사용자 확정, 2026-10-12)
- agent는 Detection(rule/code) · Manufacture · Inference(AI) 3종이다. (사용자 확정, 2026-10-12)
- LLM: Manufacture는 Opus급, Inference는 gpt-oss급을 쓴다. Detection은 LLM을 쓰지 않는다. (사용자 확정, 2026-10-12)
- Detection의 명세 확인 일정(재시작 시, 하루 1회 등)은 외부 scheduler·workflow 도구가 환경변수 설정으로 맡는다. agent는 호출되면 실행되는 API만 제공한다. webhook은 나중에 한다. (사용자 확정, 2026-10-12)
- 명세 버전 보관소는 파일 + Git 이력이다. (사용자 확정, 2026-10-12)
- Manufacture는 기계적 부분은 코드 생성, tool 설명·묶음은 LLM 보조로 만든다. (사용자 확정, 2026-10-12)
- 변경분 반영 시 사람 확인은 삭제, 권한 변경, admin·위험 동작 추가에만 거친다. (사용자 확정, 2026-10-12)
- Manufacture는 tool을 AI Pro Plus에 색인해 자연어로 검색하게 한다. AI Pro Plus는 외부 시스템이며 개발하지 않는다. (사용자 확정, 2026-10-12)
- AI Pro Plus 인증: test 환경까지는 api-key 없이 nobody 모드, production은 api key를 쓴다. (사용자 확정, 2026-10-12)
- Inference는 text 요청을 받는 자체 REST API를 기본으로 가진다. Workfluence 채팅은 타겟 종속 어댑터다. (사용자 확정, 2026-10-12)
- Inference는 채팅 창에 짧게만 답한다. 장문 결과는 메일이나 Workfluence 게시판에 올린다. (사용자 확정, 2026-10-12)
- Workfluence admin 동작은 tool로 만들지 않는다. (사용자 확정, 2026-10-12)
- 채팅 UI는 이 프로젝트의 범위가 아니다. (사용자 확정, 2026-10-12)
- 문서는 `docs/`에 phase별로 둔다. (사용자 확정, 2026-10-12)

## 부록 A. AI Pro Plus 연동 참고 (Phase 2 설계 입력)

세션 `aipro-plus-8f`가 서버 코드를 읽고 답한 내용이다. 실제 호출로 검증하지는 않았다.

- 명세: `GET {base}/openapi.json` (FastAPI 자동 생성, Swagger `{base}/docs`). 로컬 dev는 `http://localhost:28000`, nginx 경유는 `https://llm-agent.mwm.local`. 시험·운영 base URL은 사용자 확인이 필요하다.
- test 인증(nobody): 서버가 `NON_LOGIN_SERVICE=true`이면 헤더·키 없이 nobody(Admin)로 처리된다. 선택 헤더 `X-Virtual-User`로 로그·통계 집계 주체를 지정할 수 있다.
- production 인증: `Authorization: Bearer <API_KEY>`. AI Pro Plus는 키를 IDP에 위임 검증하고(타임아웃 3초), 유효하면 Admin으로 처리한다. 키별 권한 구분은 없다. 키는 IDP 관리자가 IDP 대시보드에서 발급한다. 무효이면 401 `{"detail":"Not authenticated"}`이고, 키 오류와 IDP 장애는 구분되지 않는다. IDP 모드에서는 `X-Virtual-User`가 무시된다. 그 외 규약은 test와 같다.
- 구성: 컬렉션 `POST /api/collections`(이름은 영문·숫자·`_`·`-`). 지식 등록에 `domain_id`가 필수라서 먼저 도메인을 만든다(`POST /api/domains`). 컬렉션이 이미 있으면 500이 날 수 있어 목록을 먼저 조회한다.
- 등록·수정: `POST /api/rag/knowledge` (`collection_name`, `domain_id`, `content`, `extended_content`, `source`, `point_id`). `point_id`를 지정하면 덮어쓴다. point ID는 UUID 또는 unsigned int만 가능하다. `uuid5(namespace, "targetId:toolName")` 같은 결정적 UUID를 쓰면 멱등 upsert가 된다.
- 삭제: `DELETE /api/rag/knowledge/{collection_name}/{point_id}`, 일괄 `DELETE /api/rag/bulk-delete`(`domain_id` 또는 `source` 필수), 컬렉션 통째 `DELETE /api/collections/{name}?delete_vector=true`.
- 저장 필드: `content`(이것만 임베딩), `extended_content`, `domain_id`, `source`, `created_at`. 자유 메타데이터 필드가 없다. `content`는 tool 이름+설명 요약(수백 자)으로 짧게 두고, 전체 명세·버전·scope는 `extended_content`(JSON)에, `targetId/toolName@버전`은 `source`에 둔다.
- 검색: `POST /api/rag/search` (`collection_id`, `domain_id`, `query`, `search_method`(`vector`|`text_matching`), `limit`). 서버 필터는 컬렉션과 `domain_id`뿐이다. score 임계값 파라미터가 없어 클라이언트에서 자른다. 응답에 `extended_content`가 같이 온다.
- 임베딩·청킹은 서버가 맡는다. content 1건이 1벡터다.
- 제한: rate limit 없음, nginx 기본 body 1MB 가능성, 배치 API 없음(N건 = POST N회), 등록마다 임베딩이 동기로 돈다. 오류는 `{"detail": "..."}`.

## 부록 B. Workfluence 채팅 API 참고 (Phase 4 설계 입력)

`workf` 확인과 Workfluence 저장소 `docs/P21_설계서_Chat.md`(브랜치 `impl-phase21`) 기준이다. 구현은 시작 단계이고 값은 착수 때의 가정이다.

- 방 단위 채팅(1:1 `direct`, 여럿 `group`)이다. headless 클라이언트(우리 agent)는 공개 API 토큰으로 접속한다.
- REST: `/api/v1/chat/*` (방 목록·만들기·초대·나가기, 메시지 읽기·보내기, 읽음 표시, 사용자 찾기). 읽기는 `read`, 쓰기는 `write` scope.
- WebSocket: `/api/v1/chat/ws`. `Authorization: Bearer <토큰>` 헤더로 연결한다. 토큰을 URL 질의 문자열로 보내는 것은 받지 않는다.
- 프레임: `hello`, `send`, `ack`, `message`, `room`(방 생성·초대·나감), `error`. 30초 주기 ping/pong.
- 초대 알림은 별도 webhook 없이 `room` 프레임으로 받는다. 그래서 채팅 채널의 "대기"는 WebSocket 연결을 유지하는 것이다.
- 놓친 메시지는 REST `afterSeq`로 메운다. `clientMsgId`를 붙이면 재전송이 한 번만 반영된다.
- 메시지는 평문이다(마크다운·HTML 아님). 길이 상한 기본 4000자.
- WebSocket은 OpenAPI로 표현되지 않으므로 명세 머리말과 API사용가이드를 본다. 채팅 REST가 공개 명세에 더해지면 Detection·Manufacture가 같은 방식으로 반영한다.
