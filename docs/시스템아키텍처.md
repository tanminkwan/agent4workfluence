# 시스템 아키텍처 정의서

- 작성일: 2026-10-12
- 상태: 초안
- 이 문서는 phase 0 산출물이다. 과제 범위와 결정은 [`과제정의서.md`](과제정의서.md)가 정본이다.

## 1. 핵심 결정

1. **3개 agent는 각각 독립된 Docker container로 동작한다.** 따로 빌드하고, 따로 재시작하고, 따로 시험한다.
2. **agent끼리 서로 호출하지 않는다.** Detection이 Manufacture를 불러 update 하게 하지 않는다. agent 사이의 순서는 바깥(지금은 사람, 나중에는 workflow 도구)이 정한다.
3. **각 agent는 실행 API를 하나씩 연다.**
   - Detection: **변경 식별** API 1개
   - Manufacture: **변경 반영 실행** API 1개
   - Inference: **요청 수행** API 1개 (Phase 3)
4. **agent는 호출되면 실행되는 구조만 갖는다.** 언제 실행할지(일정, 순서)는 바깥이 정한다. **지금은 사람이 curl로 실행한다.** 나중에 n8n, Windmill, Prefect 같은 workflow 도구의 한 단계로 그대로 끼울 수 있게 API를 만든다.

## 2. 구성도

```
                 사람 (curl)  ──▶  나중에: n8n / Windmill / Prefect
                    │  ①                    │  ②
                    ▼                       ▼
        ┌────────────────────┐   ┌────────────────────┐   ┌────────────────────┐
        │ detection          │   │ manufacture        │   │ inference          │
        │ container          │   │ container          │   │ container          │
        │ POST 변경 식별     │   │ POST 변경 반영     │   │ POST 요청 수행     │
        └───┬───────────┬────┘   └──┬──────┬──────┬───┘   └──┬──────┬──────┬───┘
            │ 명세 받기 │ 쓰기       │ 읽기 │ 쓰기  │ 색인    │ 읽기 │ 검색 │ tool 실행
            ▼           ▼           ▼      ▼      ▼         ▼      ▼      ▼
      Workfluence   [spec-store] ───┘  [tool-store] ──────────┘  AI Pro Plus  Workfluence
      (명세 URL)     명세 버전·변경분     tool 정의·버전              (RAG)        (API)
                                           │
                                     Manufacture LLM (Opus급)    Inference LLM (gpt-oss급)
```

- ① Detection 변경 식별을 실행하면 변경분 ID가 나온다.
- ② 그 변경분 ID로 Manufacture 변경 반영을 실행한다.
- 두 단계를 잇는 것은 바깥의 실행자다. container끼리는 공유 저장소(볼륨)의 산출물로만 이어진다.

## 3. container

| container | 역할 | 실행 API | 읽기 | 쓰기 | 외부 호출 |
|---|---|---|---|---|---|
| `detection` | 명세 수집·버전 보관·diff·변경분 산출 | 변경 식별 | — | `spec-store` | 타겟 명세 URL |
| `manufacture` | tool 생성·upgrade·실호출 검증·RAG 색인 | 변경 반영 실행 | `spec-store` | `tool-store` | AI Pro Plus, Manufacture LLM, 타겟 시험 환경 |
| `inference` | text 요청 수행, 채팅 어댑터(Phase 4) | 요청 수행 | `tool-store` | — | AI Pro Plus(검색), Inference LLM, 타겟 API |

- container마다 `GET /health`를 둔다. 실행 API가 아니라 살아 있는지 확인하는 용도다.
- **일정 실행은 agent가 하지 않는다.** "재시작 시 확인", "하루 1회 확인" 같은 일정은 외부 scheduler나 workflow 도구가 맡고, 그 일정은 그쪽의 환경변수로 설정한다. agent는 호출되면 실행되는 API만 제공한다. container 안에 scheduler를 두지 않고, 시작할 때 저절로 실행하지도 않는다.

## 4. 저장소 (공유 볼륨)

agent 사이의 연결은 파일 산출물뿐이다(과제정의서 3절 원칙 5).

| 볼륨 | 내용 | 쓰는 쪽 | 읽는 쪽 |
|---|---|---|---|
| `spec-store` | 타겟별 명세 버전(자체 Git 이력), 변경분(changeset) 파일 | detection | manufacture (읽기 전용) |
| `tool-store` | 타겟별 tool 정의와 tool 버전, 반영 기록 | manufacture | inference (읽기 전용) |

- 각 볼륨은 쓰는 container 하나만 쓰기 권한으로 붙이고, 읽는 쪽은 읽기 전용으로 붙인다.
- 모든 산출물은 `targetId` 아래에 둔다.
- 명세 보관소를 코드 저장소와 분리할지(과제정의서 미정 2번)는 이 구조로 답한다. 명세 버전은 `spec-store` 볼륨 안의 자체 Git 이력으로 두고, 코드 저장소에 커밋하지 않는다.
- 세부 디렉터리 구조와 파일 형식은 Phase 1(spec-store)과 Phase 2(tool-store) 설계에서 정한다.

## 5. 실행 API

### 5.1 공통 규칙 (workflow 도구에 끼우기 좋게)

| 규칙 | 내용 |
|---|---|
| 형식 | HTTP + JSON. 요청·응답 본문은 JSON이다. |
| 한 단계 = 한 호출 | API 하나가 한 단계를 끝까지 수행하고 결과를 돌려준다. 숨은 연쇄 호출이 없다. |
| 다음 단계 입력 | 응답에 다음 단계가 쓸 값(예: `changeSetId`)을 담는다. workflow 도구는 이 값을 다음 단계 요청에 넘긴다. |
| 멱등 | 같은 입력으로 다시 실행해도 결과가 같다. 이미 반영한 변경분을 다시 반영하면 아무것도 하지 않고 같은 결과를 돌려준다. |
| 상태 표시 | 응답에 `status`를 둔다. 분기는 HTTP 코드와 `status`로 한다. |
| 오류 | `{"error":{"code","message"}}` 한 가지 모양. `code`로 분기한다. |
| 설정 | 포트, 경로, 인증 여부는 `.env`로 둔다. |

### 5.2 Detection — 변경 식별

`POST /v1/detect`

| | 내용 |
|---|---|
| 요청 | `{"targetId": "workfluence"}` |
| 하는 일 | 타겟 명세의 변경 여부를 확인한다. 바뀌었으면 명세를 받아 새 버전으로 보관하고, 이전 버전과 diff 해서 변경분을 `spec-store`에 쓴다. |
| 응답 `status` | `changed`: 새 변경분을 만들었다. `unchanged`: 명세가 같다. |
| 응답 예 | `{"status":"changed","targetId":"workfluence","changeSetId":"…","fromVersion":"…","toVersion":"…","summary":{"added":3,"removed":0,"modified":1},"needsReview":false}` |
| 비고 | 첫 실행은 빈 버전 대비 전체를 변경분으로 만든다. 삭제·변경이 있으면(Workfluence에서는 v2 신호) `needsReview: true`. |

```bash
curl -s -X POST http://localhost:${DETECTION_PORT}/v1/detect \
  -H 'Content-Type: application/json' -d '{"targetId":"workfluence"}'
```

### 5.3 Manufacture — 변경 반영 실행

`POST /v1/apply`

| | 내용 |
|---|---|
| 요청 | `{"targetId": "workfluence", "changeSetId": "…"}` |
| 하는 일 | `spec-store`에서 변경분을 읽어 tool을 생성·upgrade 하고, 시험 환경에서 실호출로 검증하고, AI Pro Plus 색인을 갱신하고, 결과를 `tool-store`에 쓴다. |
| 응답 `status` | `applied`: 모두 반영했다. `partial`: 일부는 사람 확인이 필요해 보류했다. `noop`: 이미 반영했거나 반영할 것이 없다. `failed`: 검증 실패 등으로 반영하지 않았다(이전 tool 버전 유지). |
| 응답 예 | `{"status":"partial","targetId":"workfluence","changeSetId":"…","toolVersion":"…","tools":{"added":2,"updated":1,"removed":0},"indexed":3,"pendingReview":[{"operation":"pages.delete","reason":"위험 동작"}]}` |
| 비고 | 사람 확인 대상(삭제·권한 변경·admin·위험 동작 추가)은 반영하지 않고 `pendingReview`로 돌려준다. 승인 방법은 Phase 2에서 정한다. |

```bash
curl -s -X POST http://localhost:${MANUFACTURE_PORT}/v1/apply \
  -H 'Content-Type: application/json' -d '{"targetId":"workfluence","changeSetId":"<위 응답의 changeSetId>"}'
```

### 5.4 Inference — 요청 수행 (Phase 3)

`POST /v1/requests` — text 요청을 받아 수행한다. 요청·응답 모양, 인증, 동기·비동기는 Phase 3 설계에서 정한다(과제정의서 미정 12번). Workfluence 채팅 어댑터(Phase 4)는 이 container 안에서 같은 수행 로직을 쓴다.

### 5.5 사람이 curl로 돌리는 흐름

```bash
# 1. 변경 식별
R=$(curl -s -X POST http://localhost:${DETECTION_PORT}/v1/detect \
      -H 'Content-Type: application/json' -d '{"targetId":"workfluence"}')
echo "$R"
# 2. 바뀌었으면 반영
CS=$(echo "$R" | jq -r 'select(.status=="changed") | .changeSetId')
[ -n "$CS" ] && curl -s -X POST http://localhost:${MANUFACTURE_PORT}/v1/apply \
      -H 'Content-Type: application/json' -d "{\"targetId\":\"workfluence\",\"changeSetId\":\"$CS\"}"
```

workflow 도구로 옮길 때는 위 두 호출을 두 단계로 두고, 1단계의 `status`로 분기하고 `changeSetId`를 2단계에 넘기면 된다.

## 6. 설정

- 공통 설정과 container별 설정은 `.env`로 받는다(포트, 저장소 경로, 로그 수준).
- 실행 일정은 agent 설정이 아니다. 외부 scheduler·workflow 도구의 환경변수로 둔다.
- 타겟 설정은 타겟별 `.env`로 받는다(타겟 token, spec URL, 해시 URL, 호출 한도 등). 비밀이 든 `.env`는 Git에 올리지 않고, 변수 이름만 적은 예시 파일(`.env.example`)을 올린다.
- 외부 시스템(AI Pro Plus, LLM)의 접속 설정은 그 시스템을 쓰는 container에만 넘긴다. 예를 들어 Detection에는 AI Pro Plus나 LLM 설정을 주지 않는다.
- 파일 이름과 변수 이름 규칙은 Phase 1 설계에서 정한다.

## 7. 배포 단위

- `docker compose` 하나로 3개 container와 2개 볼륨을 올린다. container는 따로 올리고 내릴 수 있다.
- 각 agent는 자기 Dockerfile을 가진다. 공통 코드(코어 interface, 타겟 어댑터 interface, 설정 읽기)는 공유 패키지로 두고 각 이미지가 포함한다.
- 저장소 배치(안):

```
agents/
  detection/      # Dockerfile, 앱, 테스트
  manufacture/
  inference/
packages/
  core/           # 공통 interface·모델·설정 (타겟 무관)
  targets/
    workfluence/  # Workfluence 타겟 어댑터
docker-compose.yml
.env.example
```

- 배치의 세부는 각 phase 설계에서 확정한다. Phase 1에서는 `detection`과 공통 패키지만 만든다.

## 8. 미정 항목

| # | 결정 사항 | 제안 | 정할 때 |
|---|---|---|---|
| A1 | 실행 API의 인증: 지금은 사람이 내부망에서 curl로 부른다 | 시험 환경은 인증 없이 열고, 운영은 정적 Bearer 토큰(`.env`). 둘 다 설정으로 고른다 | Phase 1 |
| A2 | 변경 반영 실행이 오래 걸릴 때(tool 수 × 순차 색인) 동기 응답으로 버틸지, 작업 ID를 돌려주는 비동기로 갈지 | 처음엔 동기. 실측 후 느리면 비동기(작업 ID + 상태 조회)를 더한다 | Phase 2 |
| A3 | 실행 API 외에 조회 API(변경분 내용, 반영 기록)를 둘지 | 실행 API 하나 원칙은 지키고, 조회가 필요하면 읽기 전용 API를 따로 더한다 | Phase 1·2 |
| A4 | API 프레임워크와 기본 이미지 | Python + FastAPI(명세 자동 생성으로 workflow 도구 연동이 쉬움) | Phase 1 |
| A5 | 같은 타겟에 변경 식별·반영이 동시에 두 번 실행될 때의 처리 | 타겟 단위 잠금, 진행 중이면 409로 거절 | Phase 1·2 |
