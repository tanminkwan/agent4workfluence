# Phase 1 요구사항 정의 — Detection agent

- 작성일: 2026-10-12
- 상태: 초안
- 상위 문서: [`과제정의서.md`](../과제정의서.md) 2.1절, [`시스템아키텍처.md`](../시스템아키텍처.md) 3·4·5.2절
- 이후 변경: Phase 2에서 Detection을 타겟 창구로 보강한다(타겟 정보 조회, 실호출 검증 API, 타겟 token 보유). 요구사항은 [`phase2_manufacture/1_요구사항정의.md`](../phase2_manufacture/1_요구사항정의.md) 4.15절(FR-331~337), 설계는 [`phase2_manufacture/2_설계.md`](../phase2_manufacture/2_설계.md) 11절. 이 문서의 요구사항과 API 계약은 바뀌지 않는다.

## 1. 목표

타겟의 API 명세를 받아 버전으로 보관하고, 이전 버전과 비교해 변경분을 식별해서, 다른 서비스가 조회할 수 있게 한다. 실행은 API 호출로만 일어난다.

이번 phase의 타겟은 Workfluence 하나다. 다른 타겟의 경우는 interface만 둔다(과제정의서 1.3절).

## 2. 범위

| 포함 | 제외 |
|---|---|
| `detection` container와 이미지 빌드 스크립트 | `manufacture`, `manufacture-mcp`, `inference` |
| 공통 패키지 중 Detection이 쓰는 부분(설정 읽기, 타겟 interface, 오류 모양) | AI Pro Plus·LLM 연동 |
| Workfluence 타겟 어댑터 중 명세 수집 부분 | Workfluence 업무 API 호출(tool 실행) |
| `docker-compose.yml`(이번에는 `detection`만) | 일정 실행(외부 scheduler 몫), webhook 수신 |

## 3. 기능 요구사항

### 3.1 변경 식별 — `POST /v1/detect`

| ID | 요구 |
|---|---|
| FR-101 | 요청 본문 `{"targetId"}`를 받는다. 등록되지 않은 `targetId`면 404로 거절한다. |
| FR-102 | 해시 URL이 있는 타겟은 해시를 먼저 받는다. 마지막 보관 버전의 해시와 같으면 명세를 받지 않고 `status: "unchanged"`를 돌려준다. |
| FR-103 | 해시가 다르거나 보관 버전이 없으면 명세를 받는다. 받은 명세의 sha256을 직접 계산해 해시 URL 값과 같은지 확인하고, 다르면 저장하지 않고 오류로 돌려준다. |
| FR-104 | 받은 명세가 OpenAPI 3.x YAML로 해석되지 않으면 저장하지 않고 오류로 돌려준다. |
| FR-105 | 새 명세를 새 버전으로 보관한다. 버전 식별자는 명세의 sha256으로 한다. 받은 내용 그대로(바이트 단위) 보관하고 고치지 않는다. |
| FR-106 | 명세 버전 보관소는 자체 Git 이력을 가진다. 새 버전 보관은 커밋 하나로 남긴다. |
| FR-107 | 새 버전을 직전 버전과 비교해 변경분을 만든다. 직전 버전이 없으면(첫 실행) 빈 명세 대비 전체를 변경분으로 만든다. |
| FR-108 | 변경분은 동작 단위로 만든다. 동작은 `(HTTP 메서드, 경로)`로 식별하고, 각 동작을 **추가·삭제·변경** 중 하나로 분류한다. |
| FR-109 | 동작의 "변경"은 그 동작의 명세 조각(입력·응답·보안 scope·설명 등)이 달라진 경우다. 동작이 참조하는 공용 스키마(`components`)가 바뀐 경우도 그 동작의 변경으로 본다. |
| FR-110 | 줄 단위 diff도 함께 보관한다(사람이 확인하는 용도). |
| FR-111 | 변경분에 삭제나 변경이 하나라도 있으면 `needsReview: true`로 표시한다. Workfluence 호환 정책상 v1은 더하기만 하므로 삭제·변경은 사람 확인 대상이다. 단, 설명 문구만 바뀐 변경은 검토 대상에서 뺀다(설계 6절에서 보완). 이 판단 규칙은 타겟 설정이 정한다. |
| FR-112 | 변경분마다 `changeSetId`를 붙인다. 같은 `(fromVersion, toVersion)`에는 늘 같은 `changeSetId`가 나온다. |
| FR-113 | 응답은 `status`(`changed`/`unchanged`), `targetId`, `changeSetId`, `fromVersion`, `toVersion`, `summary`(추가·삭제·변경 수), `needsReview`를 담는다. `unchanged`이면 `changeSetId`가 없다. |
| FR-114 | 같은 명세로 다시 호출하면 새 버전이나 새 변경분을 만들지 않는다(멱등). |
| FR-115 | 같은 타겟에 변경 식별이 이미 진행 중이면 409로 거절한다(타겟 단위 잠금). |

### 3.2 변경분 조회 — `GET /v1/changesets/{changeSetId}`

| ID | 요구 |
|---|---|
| FR-121 | `targetId`와 `changeSetId`로 변경분을 돌려준다. 없으면 404. |
| FR-122 | 응답은 변경분 머리(`changeSetId`, `targetId`, `fromVersion`, `toVersion`, `needsReview`, `summary`, 만든 시각)와 동작 단위 변경 목록을 담는다. |
| FR-123 | 변경 목록의 각 항목은 동작 식별(`method`, `path`, `operationId`), 분류(`added`/`removed`/`modified`), 새 명세 조각(추가·변경일 때), 옛 명세 조각(삭제·변경일 때)을 담는다. 명세 조각은 Manufacture가 다른 곳을 보지 않고 tool을 만들 수 있게 그 동작이 참조하는 스키마까지 풀어서 담는다. |
| FR-124 | 조회는 저장소를 바꾸지 않는다. |
| FR-125 | 이 응답 모양을 Detection–Manufacture 계약으로 문서화하고, 계약 시험으로 고정한다. |

### 3.3 공통

| ID | 요구 |
|---|---|
| FR-131 | `GET /health`는 살아 있는지와 보관소 접근 가능 여부를 돌려준다. |
| FR-132 | 오류는 `{"error":{"code","message"}}` 한 가지 모양이다. `code`는 고정 문자열이다. |
| FR-133 | 자기 API의 OpenAPI 명세(`/openapi.json`)를 연다. |
| FR-134 | 인증은 설정으로 고른다. 시험 환경은 인증 없음, 운영은 정적 Bearer 토큰이다. 토큰이 맞지 않으면 401. |
| FR-135 | 일정 실행, 시작 시 자동 실행을 하지 않는다. |

### 3.4 타겟 확장 interface (구현은 비워 둠)

| ID | 요구 |
|---|---|
| FR-141 | 명세 수집은 interface 뒤에 둔다. Workfluence 구현(해시 URL + 키 정렬 YAML)만 만든다. |
| FR-142 | 해시 URL이 없는 타겟, 키 정렬이 보장되지 않는 명세(정규화 후 비교), JSON 명세를 위한 자리는 interface로만 두고 구현하지 않는다. 호출되면 "지원하지 않음" 오류를 낸다. |
| FR-143 | 변경 검토 판단 규칙(FR-111)은 타겟별 정책 interface로 둔다. Workfluence 정책만 구현한다. |

## 4. 비기능 요구사항

| ID | 요구 |
|---|---|
| NFR-101 | **설정**: URL, 경로, 포트, 인증 여부, 잠금 대기 등은 환경변수(`.env`)로 받는다. 타겟 설정은 타겟별 `.env`로 받는다. 코드에 하드코딩하지 않는다. |
| NFR-102 | **proxy**: 타겟 명세 URL이 내부 주소면 proxy를 거치지 않는다(`NO_PROXY`). 빌드 시 proxy는 host 환경변수를 `--build-arg`로 넘긴다. |
| NFR-103 | **TLS**: 시험 스택의 자체 서명 인증서를 다룰 수 있어야 한다. CA 파일 경로 또는 검증 끄기를 설정으로 고른다. 기본은 검증한다. |
| NFR-104 | **저장**: 명세 버전은 파일 + 자체 Git, 변경분과 메타데이터는 SQLite에 둔다. 모두 `spec-store` 볼륨 안이다. 저장은 repository interface 뒤에 둔다. |
| NFR-105 | **결정성**: 같은 두 명세에 대한 변경분은 늘 같다(항목 순서 포함). |
| NFR-106 | **로그**: 비밀(token)을 남기지 않는다. 명세 본문을 로그에 통째로 남기지 않는다. |
| NFR-107 | **실행 환경**: 빌드·테스트·실행 모두 container 안에서 한다. 이미지 빌드는 compose와 독립이다. |
| NFR-108 | **설계 원칙**: SOLID를 지킨다. 특히 타겟 어댑터·저장소·정책은 interface로 분리한다. |
| NFR-109 | **개발 방식**: TDD(red → green). 테스트를 먼저 쓴다. |

## 5. 인수 기준

| # | 기준 | 확인 방법 |
|---|---|---|
| AC-1 | 빈 보관소에서 첫 호출 시 전체 동작이 `added`인 변경분이 생긴다 | 시험 스택 실호출 |
| AC-2 | 명세가 같으면 두 번째 호출은 `unchanged`이고 새 버전·변경분이 생기지 않는다 | 시험 스택 실호출 |
| AC-3 | 옛 명세(저장소 사본, 동작 66개)에서 새 명세(시험 스택, 동작 75개)로 바뀐 경우, 추가된 `chat` 동작 등이 `added`로 정확히 식별된다 | 두 명세로 단위·통합 시험 |
| AC-4 | 동작 삭제, 입력·응답·scope 변경, 공용 스키마 변경이 각각 `removed`·`modified`로 식별되고 `needsReview: true`가 된다 | 손으로 만든 명세 쌍으로 단위 시험 |
| AC-5 | 변경분 조회 응답만으로 각 동작의 명세 조각을 얻을 수 있다(외부 참조 없음) | 계약 시험 |
| AC-6 | 해시 불일치, YAML 해석 실패, 등록되지 않은 타겟, 동시 실행이 정해진 오류 코드로 거절된다 | 단위·통합 시험 |
| AC-7 | `docker-compose.yml`의 `detection`을 compose로 올리고 curl로 위 흐름을 재현할 수 있다 | 수동 실행 기록 |
| AC-8 | 코드에 URL·경로·포트·token이 하드코딩되어 있지 않다 | 검토 |

## 6. 시험 자료

- 옛 버전: Workfluence 저장소 사본 `docs/spinoff/public-api/openapi.yaml` (동작 66개).
- 새 버전: 시험 스택 `https://wf.internal:8444/api/v1/openapi.yaml` (2026-10-12 기준 동작 75개, `chat` 경로 추가). `openapi.sha256` 값이 YAML 본문의 sha256과 같은 것을 확인했다.
- 경계 경우: 삭제·변경·공용 스키마 변경을 담은 작은 명세 쌍을 시험용으로 만든다.
- 시험 자료 파일은 저장소의 테스트 디렉터리에 둔다. 시험 스택의 명세는 시점에 따라 바뀌므로, 실호출 시험과 고정 자료 시험을 나눈다.

## 7. 설계에서 정할 것

- 타겟별 `.env` 파일 이름과 변수 이름 규칙
- `spec-store` 디렉터리 구조, SQLite 테이블, Git 커밋 규칙
- `changeSetId` 생성 규칙(FR-112를 만족하는 방법)
- 변경분 조회 응답의 정확한 스키마(계약)
- 오류 코드 목록
- 공통 패키지와 `detection` 앱의 모듈 구조, Dockerfile과 빌드 스크립트
